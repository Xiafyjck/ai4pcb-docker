# fsferry

在共享文件系统上摆渡命令,让**没有 SSH 入口的机器可被远程执行命令**。

前提只有两条,与具体集群无关:

1. 两台机器挂载同一个文件系统,且**挂载路径一致**;
2. 其中一台没有 SSH 入口(或你够不着),但它能读写这个共享文件系统。

典型场景:受管控的训练节点不接受任何 ssh 连入、也不联网,与外界交换数据只靠共享卷。

## 它不是什么

- **不是 FUSE 文件系统**——所以叫 `fsferry` 而不是 `ferryfs`,后者会被误读成 sshfs 那一类。
- **不是真的 SSH**:没有 PTY、没有交互式 shell、没有端口转发。要那些得让真正的 sshd 跑在这条通道上,见文末。
- **不是搬文件的工具**:共享卷本身就是文件通道,拷贝直接 `cp` 就行。

## 分层

```
src/fsferry/channel.py   传输层:把一个共享目录变成可靠消息通道(原子写 + 轮询)
src/fsferry/agent.py     应用层(远端):收命令、执行、回结果;常驻在没有 SSH 的那台
src/fsferry/cli.py       应用层(本地):投命令、取结果,即 `h200` 命令
```

分层不是摆设:日后若要让真正的 SSH 跑在这条通道上,要换的只是应用层——把消息语义扩成字节流喂给 `sshd -i`,通道本身不用重写。

## 部署

### 1. 两台机器都设通道目录

通道目录只有一个配置入口:环境变量 `FSFERRY_DIR`。不提供命令行覆盖——多一个入口就多一套优先级规则,以及出错时"到底哪个生效了"的困惑。它是部署事实(两端必须完全一致),部署时设一次就够。

选路径有两条硬要求和一条性能建议:

1. 在共享卷上,两台机器**路径完全一致**;
2. 用**绝对路径写死**,别写成 `"$SOMEVAR/fsferry"`——变量在非交互 shell 里为空时会静默变成 `/fsferry`,以 root 身份跑还真能把目录建在文件系统根下;
3. **优先挑最快的那个卷**。实测同一集群里 SSD 卷比 HDD 卷快近 8 倍(见下文延迟一节),而通道只占几 KB,没理由委屈它。

```bash
# 两台机器都加。路径按你自己集群的实际情况填,这里是示例
export FSFERRY_DIR=/<快卷>/<你的目录>/fsferry
```

没设会在启动时立刻退出,不做静默默认——两端各指向不同目录时双方都不报错、只会永远互相干等,那是最难查的一类故障。`channel.root_from_env()` 另外会拒绝相对路径和落在文件系统根下的路径。改完开个新 shell 验一下:

```bash
echo "$FSFERRY_DIR"    # 应该是共享卷上的完整绝对路径
```

### 2. 装依赖(只在能联网的那台)

> 本仓库的镜像已经在构建期 `uv tool install` 过了,容器里直接有 `h200` 和
> `fsferry-agent`,这一步可以跳过。下面是在共享卷上单独用一份 checkout 时的做法。

```bash
uv sync     # 本项目零依赖,只是建 venv 并装它自己
```

两台机器共用共享卷上的同一份 checkout。`.venv/bin/python` 是符号链接,它指向的
解释器路径也必须在两台机器上都存在;否则入口脚本明明存在,启动时仍会报
`No such file or directory`。这种情况下,在远端用 `uv --python` 选择一个两边都
存在的解释器(通常是 `/usr/bin/python3`),让 uv 重建环境即可。

### 3. 在没有 SSH 的那台启动代理

**这一步只有你能做**:用你现在启动训练任务的同一个机制(作业提交 / 容器 entrypoint / 任何能在那台机器上拉起进程的入口),把代理跑起来:

```bash
echo "$FSFERRY_DIR"        # 先确认:必须是共享卷上的绝对路径,不能是 /fsferry 之类
mkdir -p "$FSFERRY_DIR"    # 日志重定向由 shell 在进程启动前建立,目录得先在
nohup fsferry-agent > "$FSFERRY_DIR/agent.log" 2>&1 &
```

若共享 `.venv` 的 Python 链接在远端失效,可直接让 uv 使用系统 Python 启动。下面
这条形式已在 H200 上验证可用;`uv` 负责选择/构建 Python 环境,`nohup` 则保证
启动 shell 退出后代理仍继续运行,两者不能互相替代:

```bash
nohup uv run \
  --python /usr/bin/python3 \
  --project /共享卷上的/fsferry \
  fsferry-agent \
  > "$FSFERRY_DIR/agent.log" 2>&1 &
```

成功后,`heartbeat` 应每约 2 秒更新;可从另一台机器做只读探测:

```bash
h200 'hostname; whoami; nvidia-smi -L'
```

日志刻意放在通道目录里:它在共享卷上,所以**另一台机器能直接读到这台机器的代理日志**——那是你唯一能看到这台机器内部状态的窗口。

两个必须注意的环境问题:

- **代理的环境就是所有远程命令的环境**(命令继承代理进程的环境变量),所以要在已配好环境的 shell 里启动它。
- **非交互 shell 可能拿不到环境变量**。常见的 `~/.bashrc` 开头有 `[ -z "$PS1" ] && return`,只有交互式 shell 才会往下走;作业调度器、容器 entrypoint 这类非交互入口会跳过整段配置,`$XDG_*` / `$FSFERRY_DIR` 全为空。若走这类入口启动,要在启动脚本里显式 source 那份环境配置,别指望它自动生效。

代理是那台机器对外的唯一执行入口,而那台机器没有 SSH:**它挂了你没法登上去重启**,只能靠外层作业机制重新拉起。所以建议把它挂在常驻作业里,或和训练任务一起启动。

### 4. 用

```bash
h200 'nvidia-smi'
h200 'cd /path/to/repo && git log -1'
h200 --wait 3600 'torchrun --nproc_per_node 8 train/sft.py ...'
```

行为对齐 ssh 远程执行:stdout 进 stdout、stderr 进 stderr、**退出码就是远端命令的退出码**。所以它能直接进管道、进 `&&`、进脚本的 `if`,调用方不需要知道底下是个共享文件夹:

```bash
h200 'nvidia-smi --query-gpu=memory.used --format=csv' | tail -8
h200 'test -f output/ckpt/config.json' && echo "checkpoint 已就位"
```

长命令**跑着的时候就能看输出**,不用等它结束:代理把正在执行命令的 stdout/stderr 实时写在共享卷的 `live/` 下。`h200` 等了 2 秒还没等到结果时,会在 stderr 上打出一行现成的 tail 命令,照抄执行即可:

```bash
h200 --wait 3600 'python train/sft.py ...'
# h200: 仍在运行,实时看输出: tail -F $FSFERRY_DIR/live/<id>.out    ← 在另一个终端照抄
```

两个注意点:一是缓冲在**子进程手里**——程序发现 stdout 不是终端时通常转全缓冲,Python 要加 `-u`(或设 `PYTHONUNBUFFERED=1`),其他程序可加 `stdbuf -oL` 前缀,否则 tail 会一大批一大批地跳;二是跨节点可见性受共享卷元数据传播影响,tail 到的内容比远端真实进度晚几秒属正常。

## 延迟

4090 ↔ H200 跨节点实测(交错轮转测量,以排除时间漂移):

| 通道目录所在卷 | 中位 | 范围 |
|---|---|---|
| `gpfs_hdd`(机械盘) | 740 ms | 361–1445 ms |
| `gpfs_flash`(SSD) | **96 ms** | 42–149 ms |

**通道目录放在哪个卷上,是唯一真正影响延迟的因素**——差了近 8 倍,而且 SSD 上的抖动小得多。有 SSD 卷就放 SSD 卷,前提是它两机同路径可见。

反过来,**轮询周期几乎不影响延迟**。把客户端轮询上限在 20ms–500ms 之间调了一圈,交错测量下各档中位数落在 601–665ms(HDD 卷),差异完全淹没在噪声里。瓶颈是 GPFS 跨节点元数据传播本身,不是你多久看一次。

> 踩过的坑:曾有一次顺序测量显示"轮询越快延迟越高",看着还很像"快速轮询抢占元数据 token、饿死写入方"的因果故事。其实是假象——四个档位按顺序跑,期间文件系统整体在变慢,**时间漂移和处理效应混淆了**。交错重测后差异消失。测这类高噪声的东西必须交错。

对命令级用途,即使在 HDD 卷上也够用(`nvidia-smi` 自己就要 0.15–0.4s)。但脚本里要跑很多条命令时,**合并成一条只付一次往返**:`h200 'a; b; c'` 远比循环调用三次便宜。

## 协议

刻意用**纯文本文件**而不是 JSON。理由:这条通道通向一台你 SSH 不进去的机器,它坏掉时你手上只有 `ls` 和 `cat`。纯文件让你能肉眼看懂中间状态,JSON 会把这个能力挡在转义后面。

```
$FSFERRY_DIR/
  inbox/   <id>.cmd                     待执行命令,文件内容就是命令原文
  work/    <id>.cmd                     代理认领后移到这里;崩溃时留下现场
  live/    <id>.out .err                正在执行的命令的实时输出,人可 tail -F
  outbox/  <id>.out .err .exit .done    结果;done 最后写,是提交标记
  heartbeat                             代理存活证明
  tmp/                                  原子写暂存
```

两个关键设计:

- **原子性**靠"先写 `tmp/` 再 rename"。同卷 rename 是原子操作,读端永远看不到半截文件。这是 Maildir(qmail)传下来的老办法,也是 spool 目录几十年来能在共享存储上工作的原因。`live/` 是唯一的刻意例外:它就是给人实时看的"半截文件",程序间的消息交换从不读它——命令结束时内容原样经 `tmp/` 原子转正进 `outbox/`,live 文件即删。
- **可见性**只能靠轮询,**不能用 inotify**——inotify 只感知本机写入,另一台机器经共享卷写进来的文件不会触发任何事件。这是本方案最容易踩的坑。

通道坏掉时可以完全绕开客户端手工验证链路(已验证可用):

```bash
# 注意必须先写 tmp/ 再 mv,直接 echo 进 inbox/ 可能被代理读到半截
echo 'nvidia-smi' > "$FSFERRY_DIR/tmp/probe.cmd"
mv "$FSFERRY_DIR/tmp/probe.cmd" "$FSFERRY_DIR/inbox/probe.cmd"
cat "$FSFERRY_DIR/outbox/probe.out"
```

## 可调项

| 环境变量 | 默认 | 作用 |
|---|---|---|
| `FSFERRY_DIR` | 无(必须设) | 通道目录,两机同一路径。**唯一的身份配置,没有命令行覆盖** |
| `FSFERRY_POLL` | 0.05 | 代理空闲轮询周期(秒) |
| `FSFERRY_MAX_RUNTIME` | 0(不限) | 单条命令的执行上限(秒) |
| `FSFERRY_MAX_OUTPUT` | 8 MiB | 单条 stdout/stderr 上限,超出截断 |
| `FSFERRY_TTL` | 3600 | 无人取走的结果保留秒数,过期由代理清理 |

除 `FSFERRY_DIR` 外都是代理侧的调优项,有合理默认值,通常不用动。客户端只有一个命令行参数 `--wait`(默认 300 秒),跑长任务时调大。

注意 `FSFERRY_POLL` 调密**并不会降低延迟**:实测轮询周期在 20ms–500ms 之间对端到端延迟没有可分辨的影响,瓶颈在共享卷的跨节点元数据传播。想快就换卷,别调轮询。

## 安全

**这条通道就是设计上的远程代码执行**:能写 `inbox/` 的人,就能在那台机器上以代理的身份执行任意命令。

- 把 `$FSFERRY_DIR` 权限收到 `700`,别用 root 跑代理。
- 代理日志逐条记录执行过的命令,这是你的审计线索。
- 需要更紧的话,在 `agent.execute()` 里加命令白名单。

还有一层治理上的提醒:**那台机器没有 SSH 往往是有意为之**,这条通道等于绕过了那道控制。开之前先确认集群策略允许。

## 限制

- 命令**串行执行**,一次一条。诊断类用途不需要并发,串行既避免压垮训练机,也让 outbox 的时间线可读。代价是**一条命令卡住就堵住整条通道**,所以长任务一定要后台化(见下条)。
- 起长任务要后台化:`h200 'nohup torchrun ... > train.log 2>&1 &'`。代理用文件(`live/`)而不是管道收集输出,所以后台进程不会拖住这次往返(这点踩过坑:早期用 `capture_output=True`,后台进程继承管道后 `subprocess.run` 永远等不到管道关闭,一条后台命令就把整条通道永久堵死,而那台机器没 SSH 救不回来)。即便如此,长期运行的守护进程仍应自己重定向到日志文件——`h200` 那条命令返回后 live 文件即被删除,守护进程继续写只会写进一个没有名字的文件,白占磁盘且看不到。
- 无 PTY、无交互、无端口转发。
- 输出超上限会截断(截断会在 stderr 里说明)。
- 客户端等超时后,命令仍会在远端跑完,结果留在 `outbox/` 里直到 GC——可按 id 手工去取。

## 以后:让真 SSH 跑在这条通道上

如果哪天需要 VS Code Remote、端口转发或交互 shell,不用推倒重来:

- 客户端侧用 `ssh -o ProxyCommand=...`,把 SSH 的字节流接到本通道;
- 远端侧用 `sshd -i`(inetd 模式,不监听端口,直接在 stdin/stdout 上讲 SSH 协议)。

握手、认证、加密全是真的,只有最底层 TCP 被换成共享文件。要做的是把 `channel` 的消息语义扩成有序字节流(分块、序号、EOF、背压)。

代价要先知道:交互 shell 每次键盘回显都要付一个往返,秒级延迟下没法愉快打字;SSH 握手要好几个往返,建连可能几十秒(可用 `ControlMaster`/`ControlPersist` 复用连接摊掉)。所以它适合当应急通道,不适合当日常主力。
